# 组件知识辅助的代码迁移智能体：三场景验证

## 摘要

将 Windows 平台代码迁移至麒麟，或将 Intel IPP 调用替换为 VSIPL，主要成本集中在同一约定于多个调用点重复出现，以及目标运行时接口与源接口之间的多对一映射。智能体在修改代码前，先从当前工作区整理共性组件，再引入其他项目的迁移经验组件，二者合并为当前任务的迁移方案；整理与迁移在同一会话完成，最终交付工作区。报告按三个场景说明方法、验证数据与判分方式。

## 1 智能体设计

### 1.1 设计思路

迁移中的重复工作有两类：同一约定分布在多个调用点，例如线程的启动、超时与清理分散在线程、线程池、定时器三个模块；目标运行时提供另一组接口，需要整体替换调用序列并处理语义差异。前者可从当前代码识别，后者依赖既往迁移经验。逐文件修改容易局限于当前文件，或在各调用点采用各自写法。为此，智能体先整理组件，再进入迁移。

### 1.2 两类组件

共性组件取自当前工作区，集中描述分散在多个文件中的同一约定：契约内容、需要同步修改的位置、验证依据。以线程为例，组件记录启动、等待结束、超时与线程局部存储清理的调用点，以及调用方默认依赖的行为。

迁移经验组件取自其他项目的迁移记录，描述同类代码的替换方式：源侧模式、目标侧模式、逐条映射、语义偏差与已知问题。组件以模式与映射为核心，文件名与参数由智能体结合当前代码确定。

两类组件按能力标签与调用点上下文关联，形成迁移方案，明确修改位置、映射关系与验证项。一个经验组件可服务多个共性组件；同一段线程代码迁移至两种目标运行时，映射关系相应调整。

### 1.3 工作流程

组件整理与迁移在同一会话完成，上下文保持连续。系统提示将流程固定为五个阶段，每个阶段配有受控工具，工具作用范围限于当前工作区。

1. 扫描工作区：读取生产代码、公共头文件、调用方与构建入口，按模块与调用关系划分。
2. 抽取共性组件：依据结构重复与语义相似生成候选，归纳契约、调用点与证据。
3. 抽取迁移经验组件：收集其他项目的代码差异、提交版本、问题记录与测试，标注项目、时间与数据划分；对齐迁移前后代码，归纳映射规则与语义差异，并在留出样例上回放验证。
4. 审核发布：检查映射关系、调用点覆盖与适用边界，冻结组件版本。
5. 检索与迁移：依据当前任务匹配两类组件，生成迁移方案，写入工作区组件目录，据此完成修改、构建与测试。

判分对象为智能体最终交付的工作区。

### 1.4 信息边界

组件整理阶段使用智能体可见范围内的材料：当前工作区的源码、头文件、调用方、公开测试，以及其他项目的迁移记录。参考输出、隐藏测试与评测命令保留在评测侧。历史记录按项目与时间划分，建库仓库与测试仓库分属两个集合；任务集与建库规则预先确定，建库人与评测人分开。建库所用迁移记录取自已预置任务的上游目标平台实现（任务包的 `gold/`），不取智能体运行产出的代码；智能体运行结果只用于评测。

### 1.5 对照设置

对照条件采用直接迁移，省略组件整理阶段。两组使用同一模型、题面、任务镜像、构建与判分命令。组件构建耗时单独记录，迁移阶段预留充足运行时间。为区分“增加资料”与“整理资料”的作用，对照条件同样获得同一批历史迁移记录；两组仅在整理环节区分。

三个场景的题目均来自固定版本的上游代码。表 1 列出数据规模、切分方式与判分办法。

### 2.1 Windows → 麒麟

麒麟场景按仓库切分，建库仓库与测试仓库分属两个集合。libuv 与 libarchive 建库，libgit2 试跑，POCO、nginx、curl、opencv 测试。25 个任务包中，14 个为核心测试题（POCO 7、nginx 4、curl 3），另有 3 个边界题、1 个负控题与 1 个合成题。边界题考察适用性判断，负控题考察平台能力差异的识别与说明；三类题目单独统计。

### 2.2 IPP → VSIPL

IPP 场景包含 20 个组件级任务，源快照随包固定，目标为 VSIPL 1.3 的 jvsip。函数级 6 个、模块级 9 个、仓库级 5 个；真实项目 8 个、合成任务 12 个。映射难度为一对一 9 个、组合实现 10 个、自行实现 1 个。判分环境仅提供 jvsip，IPP 符号清零后，以隐藏输入与 IPP 版基准输出比对数值与边界行为。

### 2.3 CUDA → MUSA

CUDA 场景包含 20 个算子任务，源为 MultiKernelBench 固定快照与 PyTorch 参考语义，目标为 MTT S4000、MUSA SDK 5.2.0 与 torch_musa。函数级 6 个、模块级 7 个、仓库级 7 个，提交物为单个 Python 文件。判分调用上游评测器，完成编译、五次比对与反作弊检查，并通过 CUDA 接口清除与内核结构两项检查。正控为 2 份上游样例与 18 份自写实现，20 道题均已在真机通过。

### 2.4 数据边界

三个场景均固定源码版本与许可证。隐藏测试、参考解与基准输出保留在评测侧；建库语料与测试集按仓库或数据集隔离；正控、边界与负控题目单独统计。当前题目以组件级迁移为主：多数可见源码为单个文件，多文件改动集中于少数仓库级题目。现有数据可支持“重复接口契约、跨调用点一致”类迁移的验证；更大规模的客户代码留作后续对象。

主指标为构建、数值、旧接口清除、隐藏测试四项全部通过的通过率；分项通过率单独报告。成本以单题模型调用量、运行时间与工具调用次数衡量。配对比较报告同题两组差值。辅助指标包括检索命中率、检索精度、调用点覆盖率、跨位置一致性差异与回归率。

### 3.2.1 Windows → 麒麟：配对结果

题目为 POCO Foundation 1.13.3 的四个 POSIX 后端文件（File、FileStream、DirectoryIterator、Path），Windows 实现保留可见，目标为麒麟 V10 SP3（GCC 13.3 / CMake 3.16.5）。隐藏检查在复制路径上注入 EINTR 与 1 字节短写，并检查复制到自身时内容与大小不变。两组结果：

| 指标 | 直接迁移 | 组件方法 |
|---|---|---|
| 最终判定 | fail | pass |
| 构建 | ok | ok |
| 隐藏行为测试 | fail（复制到自身，`poco_fs_sensitivity.cpp:129/131`） | pass（敏感检查 + 5 个公开套件 `OK (72 tests)`） |
| 回归 | 短路 | pass（`ThreadTest`、`SharedLibraryTest`，`OK (22 tests)`） |
| 旧接口清除 / 目标接口 | 短路 | pass / pass |
| 模型调用（迁移 + 检索） | 63 | 34 + 5 |
| 工具调用 | 66 | 51 |
| 输入 / 输出 token | 643,099 / 64,770 | 582,138 / 57,674 |
| 端到端时长 | 2,283 s | 2,020 s（检索 23 s） |
| 判分耗时 | 1,250 s | 1,211 s |

直接迁移的 `copyToImpl` 在 `open(destination, O_CREAT|O_TRUNC|O_WRONLY)` 之后才进入复制循环，全文没有设备号/索引节点比较；复制到自身时 `O_TRUNC` 先清空源文件，因此内容与大小两项检查失败。同一失败在 3 次有敏感检查结果的直接迁移运行中重复出现；组件方法的两次运行均通过全部判分门，参考实现（gold）同样通过，说明题目可解、判分门未被放宽。

组件方法这一侧的消费记录显示：检索返回 1 个构件，迁移智能体读取卡片后明确判断其请求对象/回环架构不适用于 POCO，但按卡片中的 POSIX 映射规则实现；交付实现包含复制前的 `st_dev + st_ino` 比较、读写的 EINTR 重试，以及把 `access()` 用于可读/可写/可执行判断，同时保留 POCO 的异常错误模型而没有照搬源侧的 `-1 + errno` 编码。也就是说，使用侧在套用前检查了卡片声明的适用条件，而不是整段复制。

该题只由“复制到自身”一条规则区分两组；两组的其余敏感检查结果一致。直接迁移在隐藏检查失败后短路，未执行 72 项公开测试与 22 项回归，因此无法与组件方法逐项比较。单次运行的二值结果只能说明差异存在，不构成通过率估计。

### 3.3 消融与边界

消融实验分为仅共性组件、仅迁移经验组件、两类同时提供三组，评估各自贡献。边界题报告判断正确率，负控题报告说明完整度。最后计算建库成本的单题摊销值与收回成本所需题数。

## 4 结论

Windows → 麒麟 的配对结果显示：在存在隐藏行为判别点的仓库级迁移任务上，先从已发布的迁移经验组件库取用构件、再迁移，比直接迁移可靠。直接迁移 0/1，组件方法 1/1；两组构建均通过，差异集中在“复制到自身”的身份判断，且该失败在直接迁移的多次运行中稳定复现。组件方法同时通过隐藏检查、72 项公开测试、22 项回归与旧接口/目标接口检查，参考实现亦通过全部门，排除了判分门过严或题目不可解。

成本上，组件方法在该题没有增加开销：39 次模型调用、34 分钟，低于直接迁移的 63 次、38 分钟；检索阶段 23 秒、5 次调用，组件库物化为 1 个构件、6 个文件，运行期没有新增抽取包。节省来自卡片直接给出缺失的 POSIX 语义，减少了智能体的试探与返工。

机制上有两点需要与“资料更多所以更好”区分开。第一，使用侧先检查卡片声明的适用条件：智能体认定卡片的请求对象/回环架构不适用于 POCO，只采纳 POSIX 映射规则，并保留了任务原有的异常错误模型，说明效果来自按条件筛选知识，而不是整段照搬。第二，卡片由既有抽取与审核流程发布：初次审核为 rework，修订一轮后 publish；审核闸门能拦住事实性错误，但卡片仍包含构建顺序与个别完整调用序列，抽象层级尚未达到“只给规则、不给步骤”的目标。

结论的边界：每条件仅 1 次运行；该题只有一条判别规则；消融（仅共性组件、仅经验组件）尚未在本题执行；IPP → VSIPL 与 CUDA → MUSA 两组数据待补。实验期间修复了 agent view 的构建文件可见性与回归命令的加载路径，最终两组均在修复后重新运行，隐藏测试未改动、判分门未放宽。当前证据支持“该组件在该任务上带来可靠性与成本优势”，不支持对方法整体迁移能力的普遍外推。
