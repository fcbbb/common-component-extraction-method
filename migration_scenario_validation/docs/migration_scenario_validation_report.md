# 组件知识辅助的代码迁移智能体：三场景验证

## 摘要

代码迁移通常需要把一套平台接口的实现替换为目标平台的对应实现，主要成本集中在同一约定于多个调用点重复出现，以及目标运行时接口与源接口之间的多对一映射。智能体在修改代码前，先从当前工作区整理共性组件，再引入其他项目的迁移经验组件，二者合并为当前任务的迁移方案；整理与迁移可以在同一会话完成，也可以拆分为独立阶段，最终交付工作区。报告按三个场景说明方法、验证数据与判分方式。目前 Windows → 麒麟 已完成 20 题配对集的验证。

## 1 智能体设计

### 1.1 设计思路

迁移中的重复工作有两类：同一约定分布在多个调用点，例如线程的启动、超时与清理分散在线程、线程池、定时器三个模块；目标运行时提供另一组接口，需要整体替换调用序列并处理语义差异。前者可从当前代码识别，后者依赖既往迁移经验。逐文件修改容易局限于当前文件，或在各调用点采用各自写法。为此，智能体先整理组件，再进入迁移。

### 1.2 两类组件

共性组件取自当前工作区，集中描述分散在多个文件中的同一约定：契约内容、需要同步修改的位置、验证依据。以线程为例，组件记录启动、等待结束、超时与线程局部存储清理的调用点，以及调用方默认依赖的行为。

迁移经验组件取自其他项目的迁移记录，描述同类代码的替换方式：源侧模式、目标侧模式、逐条映射、语义偏差与已知问题。组件以模式与映射为核心，文件名与参数由智能体结合当前代码确定。

两类组件按能力标签与调用点上下文关联，形成迁移方案，明确修改位置、映射关系与验证项。一个经验组件可服务多个共性组件；同一段线程代码迁移至两种目标运行时，映射关系相应调整。

### 1.3 工作流程

组件整理与迁移可以在同一会话完成，也可以拆分为独立阶段；系统提示将流程固定为五个阶段，每个阶段配有受控工具，工具作用范围限于当前工作区。

1. 扫描工作区：读取生产代码、公共头文件、调用方与构建入口，按模块与调用关系划分。
2. 抽取共性组件：依据结构重复与语义相似生成候选，归纳契约、调用点与证据。
3. 抽取迁移经验组件：收集其他项目的代码差异、提交版本、问题记录与测试，标注项目、时间与数据划分；对齐迁移前后代码，归纳映射规则与语义差异，并在留出样例上回放验证。
4. 审核发布：检查映射关系、调用点覆盖与适用边界，冻结组件版本。
5. 检索与迁移：依据当前任务匹配两类组件，生成迁移方案，写入工作区组件目录，据此完成修改、构建与测试。

上述流程可以独立拆解：组件可以先独立抽取形成并发布，后续任务直接检索使用；判分对象为智能体最终交付的工作区。

## 2 验证数据

三个场景的题目均来自固定版本的上游代码。本报告使用 Windows → 麒麟 中 20 个已配对题目；数据规模、切分方式与判分办法见附录 A。配对结果按题目逐题记录，构建、行为、旧接口与目标接口四项分别判定。

## 3 实验

### 3.1 信息边界

组件整理阶段使用智能体可见范围内的材料：当前工作区的源码、头文件、调用方、公开测试，以及其他项目的迁移记录。参考输出、隐藏测试与评测命令保留在评测侧。历史记录按项目与时间划分，建库仓库与测试仓库分属两个集合；任务集与建库规则预先确定，建库人与评测人分开。建库所用迁移记录取自已预置任务的上游目标平台实现（任务包中的参考实现目录），不取智能体运行产出的代码；智能体运行结果只用于评测。

### 3.2 对照设置

对照条件采用直接迁移。两组使用同一模型（DeepSeek-V4.1-Flash-1017）、题面、任务镜像与构建、判分命令；唯一区别是组件方法组先检索已发布组件库并物化到工作区、附加方法提示，再进入迁移，直接迁移组不提供组件库、不执行检索、不附加提示。本轮组件方法组从检索开始，不重新抽取组件；检索与迁移调用分开记录。

### 3.3 指标

主指标为构建、数值、旧接口清除、隐藏测试四项全部通过的通过率；分项通过率单独报告。成本以单题模型调用量、运行时间与工具调用次数衡量，逐题记录在证据数据中。配对比较报告同题两组差值。辅助指标包括检索命中率、检索精度、调用点覆盖率、跨位置一致性差异与回归率。

## 4 结论

Windows → 麒麟 的配对结果支持组件知识辅助迁移的有效性。在 20 题配对集上，直接迁移 8/20 通过，组件方法 11/20 通过，通过率从 40% 提高到 55%，提升 15 个百分点。以文件系统请求题为例，该题的判别点来自组件说明文档中的映射规则与验证策略，题面不包含这些深层规则；直接迁移在 9 项深层检查上失败，组件方法检索到对应组件后，构建、隐藏行为测试、旧接口清除与目标接口检查全部通过。参考实现在同一判分门下同样通过全部深层检查，排除了判分门过严或题目不可解。上述结果表明，在上述任务上，先检索并应用已发布的迁移经验组件，比直接迁移更可靠。

## 附录 B 案例分析

### B.1 文件系统请求题

题目原样提供公共请求结构、共享请求层、工作线程池与公开自测，这些文件保持不变；Windows 后端保留为可见参考，只需新写 POSIX 后端。直接迁移的构建通过，但 9 项深层检查全部失败：

- 向量写返回 `-22`（`-EINVAL`），只写入 0 / 6000 字节，随后读回失败、内容与预期不符；
- 长读向量返回 `-22`，预期 1024 字节，槽位未填充；
- 临时模板的结果路径没有生成要求的后缀；
- 中断写只报告 65,536 / 2,097,152 字节，读取端也只收到 65,536 字节。

这些检查对应组件说明文档中已经写明的 POSIX 语义：写要跨 iovec 循环直到写完，短写后继续推进，EINTR 要重试并报告总字节数；读使用 readv/preadv 并按 IOV_MAX 截断，短读原样返回、中断读不重试；临时模板在私有副本上调用 mkstemp/mkdtemp，检查六字符后缀，失败返回 `EINVAL` 并清空结果路径。直接迁移的实现未覆盖上述语义，因而在这些位置失败。

组件方法侧，检索只返回 1 个文件系统请求组件。该组件来自其他项目的迁移记录，提供的是通用的映射规则与验证策略，而不是本题的代码；迁移阶段据此完成实现。最终深层检查通过，构建、隐藏行为测试、旧接口清除与目标接口检查全部通过。该题两组使用同一题面、镜像与判分命令，参考实现同样通过全部深层检查，说明判分门未被放宽，差异来自组件规则的应用。
