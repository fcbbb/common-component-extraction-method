## 0. 一句话

V2 把验证单位从“单题”改成“库 + 任务族”：先在一个大型库上完成任务盲的组件抽取、审核、发布和冻结，再让同族迁移任务共享这份冻结库；**任务说明只表达外部契约，实现细节全部留在求解空间**，由 agent 在源码、目标库和测试反馈中自行确定。

## 1. 目标与定位

V2 的目标是验证组件方法在代码迁移中的优势，具体回答三个问题：

1. 预建的冻结组件库能否覆盖同族迁移任务所需的共性知识；
2. 使用冻结库的任务族能否在通过率、单位成本或一致性上优于直接迁移；
3. 这些收益能否归因于组件库的内容，而非额外的上下文或额外预算。

V2 的定位是**方法验证场景**：用少量真实、合理的库和任务族，把组件方法的优势机制完整地跑通并测量出来。真实 benchmark、排行榜、跨模型普适结论属于后续工作，V2 的结论限定在设计范围内。

### 1.1 组件方法在迁移中的优势机制

一个组件是从多个代码位置归纳出的稳定实现、协作协议、调用点清单和证据。迁移场景里，它转化为三样东西：

1. **一次决策**：同一源码约定只需确定一次目标映射；
2. **一致应用**：同族的多个调用点采用同一套约定；
3. **改动地图**：相关代码位置、调用方和边界完整可见。

这三样东西对应四类任务条件：

- 同一模式在至少 3 个位置出现，共性真实存在；
- 行为契约隐含在多个调用点的共同假设里，需要跨位置归纳；
- 库的规模超过单次上下文可覆盖的范围，需要定位和索引；
- 多个任务共享同一份冻结库，复用成本可以摊销。

V2 的任务设计围绕这四类条件展开。

## 2. V1 与 V2 的对照

V1 建立了可复现的任务包、判分链路和三臂入口，完成了组件级迁移的诊断覆盖。V2 在此基础上把验证目标对齐到组件方法的复用命题。

| 维度 | V1 | V2 |
|---|---|---|
| 验证单位 | 单题 | 库 + 任务族 |
| 组件库 | 每个 attempt 从当前任务工作区现建 | 任务前 task-blind 预建、审核、发布并冻结，全族共享 |
| 题目来源 | 单文件或单后端 | 大型库中的多个子系统 |
| 任务说明 | 包含公式、文件名、函数级契约 | 只写外部契约、目标环境与验收口径 |
| 工作区 | 保留参考实现的孪生代码 | 保留头文件、调用方、构建入口与公开测试；参考实现位于评测侧 |
| 隐藏测试 | 单点数值用例 | 族内全覆盖、跨调用点一致性、回归 |
| 实验条件 | A / B | A / B / B0 / C |
| 指标 | 通过率、调用数、耗时 | 通过率、复用率、摊销成本、一致性、回归 |

## 3. 任务说明：只写外部契约

这是 V2 的核心约束。任务说明是迁移合同，它把“做什么”和“验收什么”说清楚，把“怎么做”完整留给 agent。

### 3.1 任务说明回答三个问题

1. **迁移什么、迁到哪里**：源模块、目标运行时、任务边界；
2. **迁移后的外部可观察行为是什么**：公共接口、输入输出、数值口径、错误语义、状态与生命周期、所有权与线程约束；
3. **如何验收**：构建入口，以及被覆盖的外部行为。验收以行为描述，不写测试名、隐藏用例、门禁实现或评测命令。

### 3.2 任务说明的组成

| 要素 | 内容 | 示例 |
|---|---|---|
| 迁移目标 | 源模块与目标运行时 | “把 `src/dct_ipp.c` 迁移到 VSIPL 1.3 (jvsip)” |
| 公共接口 | 头文件签名、构建入口、产物 | “沿用 `include/aubio_dct.h` 的公共接口，产物为 `libaubiodct.a`” |
| 可观察行为 | 输入输出、数值口径、错误语义、状态与生命周期 | “正交 DCT-II/III 往返一致；`new_aubio_dct(0)` 返回 NULL” |
| 目标环境 | 目标库、工具链、可用依赖 | “VSIPL 1.3 C、libm、CMake” |
| 验收口径 | 构建入口与行为覆盖范围 | “验收覆盖往返一致性与 n=1..1024 的边界” |

### 3.3 实现细节属于求解空间

以下内容由 agent 在源码、目标库头文件、文档和测试反馈中自行确定：

- 算法与公式；
- 目标 API 的选择与调用序列；
- 需要创建或修改的文件与目录布局；
- 参考实现的组成与结构；
- 实现步骤与工作计划。

任务说明表达的是行为合同；实现路径由 agent 自己走。

### 3.4 写法示例

V1 的 DCT 说明给出了 DCT-II 公式、归一化常数和目标实现路径。V2 的说明写成契约：

```yaml
spec: |
  src/dct_ipp.c 提供 new_aubio_dct / aubio_dct_do / aubio_dct_rdo。
  把它迁移到 VSIPL 1.3 (jvsip) 运行时，保持 aubio 其他后端所依赖的
  正交 DCT-II / DCT-III 行为、生命周期和错误语义。
  验收覆盖 n=1..1024 与往返一致性。
  目标环境提供 VSIPL 1.3 C 与 libm。
```

这段说明表达了迁移目标、外部行为、目标环境和验收口径。公式、目标 API、文件位置和调用序列由 agent 从 aubio 的平行后端、VSIPL 头文件和测试反馈中归纳。

平行实现本身就是契约证据：aubio 的 kissfft、fftw 等后端与 IPP 后端共同表达了同一个行为合同。组件抽取从这些平行实现中归纳契约，任务说明只描述合同本身。

### 3.5 写作检查表

一份合格的任务说明满足以下七项：

- 迁移目标与边界清晰；
- 公共接口与构建入口明确；
- 外部行为可观察、可测试；
- 验收口径完整；
- 目标环境与可用依赖明确；
- 实现路径保留在求解空间；
- 题面只含契约与工作区信息，不含数据集元数据、仓库/commit、评测命令、门禁与隐藏测试。

七项齐备，任务说明就完成了它的职责。

### 3.6 题面渲染

任务说明不是孤立的一段文本：agent 实际收到的是 `shared/harness/agent_prompt.py`
渲染出的题面，由**标题、spec、目标环境、工作区、构建命令与提交方式**组成。
渲染器不读取 `scenario` / `level` / `family` / `sequence` / `difficulty`，不输出
`source.repo` 与 `source.commit`，也不输出 `hidden_tests`、`gates` 或 runner 命令。
构建命令取 `agent_build_command()`（测试开关为 OFF），judge 的 `build.command`
只用于判分。

工作区由 `shared/harness/agent_view.py` 生成：测试目录、`TASK.md`、`cppignore`
以及 `prepare.remove` / `prepare.remove_globs` 列出的实现文件都不会进入 agent
视图；judge 侧会先从 pristine 树删除这些实现，再叠加 agent 的产物。

`tools/lint_dataset.py` 会真实渲染每个任务的题面并检查上述约束；`verify_task.py`
检查物化后的 `work/` 不残留被移除文件。两条检查都失败即数据集不合格。

## 4. 库优先的任务构造

### 4.1 库的选择标准

- **规模**：5k 行以上，包含多个子系统；
- **共性**：同一模式在至少 3 个代码位置出现；
- **可判分**：上游测试或行为探测可以离线运行；
- **可抽取**：源侧生产代码、调用方和构建文件结构清晰；
- **可冻结**：固定 commit，依赖可获取。

### 4.2 组件库的构建流程

1. 冻结库快照；
2. 在任务信息引入之前完成 task-blind 抽取，语料为源侧生产代码、调用方和构建文件；
3. 经审核、准入和发布流程形成组件库；
4. 记录库版本与内容 hash，冻结；
5. 同族全部任务读取同一个冻结版本。

### 4.3 迁移组件的内容

一个迁移组件包含四部分：

- **稳定实现**：在多个位置重复出现的实现或骨架；
- **协作协议**：调用方与实现之间的约定，包括缩放、布局、错误码、所有权、生命周期和线程约束；
- **调用点清单**：使用该组件的代码位置及其上下文；
- **证据与边界**：支撑该组件成立的源码证据和适用范围。

### 4.4 任务族结构

| 类型 | 结构 | 组件的收益 | 判分重点 |
|---|---|---|---|
| 模式族 | 同一 wrapper 或协议出现在多个模块，一次迁移多个调用点 | 一次决策、统一应用 | 全部调用点通过 + 跨模块一致性 |
| 隐含契约 | 缩放、布局、错误语义、所有权只体现在多个调用点的共同假设里 | 契约发现 | 边界、状态、错误语义 |
| 定位型 | 库有数千文件，任务要求改齐某个 API 家族的全部调用点 | 改动地图 | 遗漏调用点即失败 |
| 顺序族 | 同一库的 T1…Tn，T1 建库成本最高，后续任务复用 | 成本摊销 | 首题与后续题的成本曲线 |

## 5. 三个场景的 V2 设计

### 5.1 Windows → 麒麟（主场景）

**库**：POCO Foundation、libuv 或 nginx，三者都具备清晰的平台层边界和多子系统结构。

**抽取语料**：Win32 平台实现、公共头文件、调用方和构建文件。参考 POSIX/Unix 实现保存在评测侧。

“先抽取、再围绕组件出题”是**时序**约束（任务出现前建库、全族共享同一冻结版本），
不是语料范围约束。任务族的 gold 实现（`*_POSIX.cpp` / `*_UNIX.cpp`）必须排除在
抽取语料之外；如果库从 gold 抽取，B 臂拿到的就不是组件知识，而是答案本身，
A/B 差异无法归因于组件方法。`freeze.yaml` 的 `snapshot.evaluator_side` 和
`freeze_library.py` 的 `snapshot` / `verify` 会强制这条边界。

**任务工作区**：头文件、调用方、构建入口和公开测试。agent 从这些材料中恢复平台层行为。

**任务族**：`thread`、`file`、`path`、`shared_library`、`rwlock_semaphore`、`foundation_full`，共 6 题。

**组件示例**：错误与异常协议、句柄所有权、线程状态与 TLS、路径编码、同步原语协议。

**判分**：多个上游测试套件 + 跨模块一致性检查 + 回归检查。

**任务说明**：描述每个平台层的公共行为和验收口径，例如线程的启动/加入/超时唤醒/优先级/TLS 清理。平台 API 的选择、文件布局和实现步骤由 agent 从调用方、头文件和测试反馈中确定。

### 5.2 CUDA → MUSA

**库**：MultiKernelBench 快照，本身就是“多算子共享模板”的库。

**抽取语料**：算子源码、参考 PyTorch 实现和 harness。参考 MUSA 实现保存在评测侧。

**任务族**：elementwise（relu、leaky_relu、sigmoid、swish、softmax）、reduction（sum、cumsum、argmax、layer_norm）、matmul-attention（matmul、conv2d、sdpa、gqa）、loss（mse、cross_entropy、cosine）。

**组件示例**：`load_inline` 模板、tiling、reduction tree、broadcast/indexing、dtype 处理、launch config。

**判分**：族内全部算子 + 边界 shape + 数值容差 + 目标 API 检查 + 计算算子约束。

**任务说明**：描述算子语义、输入输出、shape/dtype 规则、数值容差和提交契约。kernel 结构与 MUSA API 由 agent 自行确定。

### 5.3 IPP → VSIPL

**路线 A（主推）**：合成一个 5k–20k 行的 DSP 应用库，包含自研 IPP wrapper 层和 8–12 个业务模块。抽取语料为 wrapper、业务模块和调用方；任务族为 wrapper 迁移加模块组迁移。

**路线 B（备选）**：把 IPP 场景定位为 API 映射诊断场景，V2 的主结论由 Windows 和 CUDA 两个场景承担。

**组件示例**：FFT 缩放、CCS/Perm 布局、流式状态、窗函数约定、错误处理。

**任务说明**：描述模块的外部行为和验收口径。算法公式、目标 API、文件布局由 agent 从平行后端、VSIPL 头文件和测试反馈中归纳。

## 6. 判分与门禁

每个任务声明四类门禁，并明确各自的适用范围：

| 门禁 | 通过条件 |
|---|---|
| 构建 | 在目标运行时上完成配置与构建 |
| 行为 | 公开测试与隐藏测试全部通过 |
| 目标 API | 构建产物或源码中检测到目标 API 的实际使用 |
| 回归 | 既有功能测试保持通过 |

公开测试表达验收口径，供 agent 自检；隐藏测试覆盖族内全部调用点、边界条件、状态与错误语义以及跨模块一致性。门禁结果按 `pass` / `fail` 记录，每个任务声明门禁的适用范围，结论按任务口径汇总。

## 7. 实验设计

### 7.1 条件

| 条件 | 组件库 | 作用 |
|---|---|---|
| A | 无 | 直接迁移基线 |
| B | 任务前预建并冻结，全族共享 | 验证组件方法的复用收益 |
| B0 | 每个 attempt 现建 | 消融：区分“复用”与“抽取” |
| C | 与任务无关的库组件 | 对照：区分“库内容”与“额外上下文” |

### 7.2 预算与统计

- 四个条件使用同一模型、同一任务镜像、同一预算（步数、token、墙钟）；
- 建库成本单独记录，按任务数摊销；
- 每个条件至少 3 次运行，按任务配对汇总；
- 任务说明、公开测试、判分命令在四个条件之间保持一致。

### 7.3 指标

| 指标 | 定义 |
|---|---|
| 通过率 | 构建、行为、目标 API、回归四项全部通过的任务比例 |
| 组件复用率 | 使用至少一个库组件的任务比例 |
| 检索命中率 | 检索返回的组件在最终补丁中被采用的比例 |
| 摊销成本 | 建库成本 / 任务数 + 单题成本 |
| 一致性 | 同一约定在多个调用点的实现差异数量 |
| 回归率 | 既有功能测试出现失败的次数 |
| 成本曲线 | 首题与后续题的单位成本变化 |

### 7.4 成功判据

V2 在以下条件同时成立时给出正向结论：

- B 的通过率高于 A，且优势集中在定位、契约发现和一致性类任务；
- B 的摊销成本低于或接近 A；
- B 优于 B0，说明收益来自冻结库的复用；
- B 优于 C，说明收益来自库内容本身；
- 每个任务族至少有 2–3 道题在 A 下因结构性原因失败、在 B 下通过。

## 9. 与 V1 的关系

V1 的 60 道题继续作为组件级迁移的诊断集，用于检查 API 映射、数值约定和构建链路。V2 新增库优先的任务族，承担组件方法优势的主结论。两套任务共用同一套判分器、镜像和模型路由，结果分开汇报。

## 10. 对外表述边界

V2 的结论限定在设计场景内：它说明组件方法在具备共性、隐式契约、定位压力和复用结构的迁移任务中带来的收益。真实 benchmark 的构建、排行榜和跨模型普适性属于后续工作。
