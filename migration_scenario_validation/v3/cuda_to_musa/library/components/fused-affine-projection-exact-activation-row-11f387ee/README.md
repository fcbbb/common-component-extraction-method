# Fused affine projection + exact activation + row normalization rebuilt as MUSA extension kernels

- Kind: transformation
- Capability: `other`
- Derived from: `s2_matmul_gelu_softmax`
- Applies to: x86_64

## When to use

Use this when the evaluation's compute-path policy requires every forward computation to run inside custom device kernels: tensor-library matmul, activation and normalization calls reachable from the forward path are rejected even though the runtime does provide equivalent high-level operators, so the device-extension path (host prototype plus device kernel source, inline-compiled when the module is imported) is imposed by that policy rather than by any gap in the platform's operator coverage. The source side being replaced expresses one operator as a chain of host tensor-library calls over a two-dimensional float32 batch: an affine projection (weight stored output-first, plus a bias), the exact non-approximated activation variant, and a normalization along dim 1 (the feature axis). A framework layer object may still be constructed in the constructor as a parameter container, because it contributes no compute that the forward path reaches; only allocation and layout helpers remain available inside the forward. It assumes the caller instantiates the rebuilt class with the same constructor arguments as the source class from the same seeded random state and compares outputs within a small absolute/relative tolerance (about 1e-4 on float32), so parameter layout, axis choice, activation variant and dtype must all match the source contract. A missing host compiler or device-runtime header is not a reason to relax this: it surfaces as an import-time build failure of the extension.

## Procedure

1. Pin the observable contract first: output shape and dtype, the normalization axis, the activation variant, and the numeric tolerance; every later decision is subordinate to these and none may drift.
2. Choose the fusion boundary by reduction ownership: a projection block that owns only an output tile cannot compute a row-wide normalization, so plan projection and epilogue as separate launches unless one block provably owns a whole output row.
3. Fix the weight orientation inside the kernel index arithmetic before writing launch code, so the stored parameter layout is consumed directly and no runtime transposed copy is ever needed.
4. Decide the row pass structure up front (reduce for the maximum, reduce for the sum of exponentials, then write the normalized values) and size the shared reduction scratch together with the launched block width, so the tree and the scratch cannot disagree.
5. Validate shapes, dtype and bias length before allocation and before launch, and add an explicit launch-status check after each launch, so a mis-sized launch is reported at the call site rather than at the next synchronization.
6. Allocate the output on the input's options, have the kernels overwrite every element, and return a caller-owned tensor without freeing or aliasing caller buffers.
7. Preserve the parameter container, constructor signature and class contract the caller expects, so seeded initialization reproduces the reference weights exactly.
8. Bring the port up in stages: projection alone, then projection plus activation, then the full normalized operator, each compared against the source-side chain on the same inputs.

## Mapping rules

- General: an affine projection whose parameter container stores the weight as (out_features, in_features) with a bias of length out_features maps to a tiled GEMM kernel that consumes that stored layout as-is, reducing over the second parameter axis and adding the bias per output column; the fallback is to transpose a copy of the parameter once and index reduction-last, which is correct but costs one full-size copy and still requires the multiply itself to run in a custom kernel, because the compute-path policy rejects library matmul in the forward.
- General: an input tensor whose strides are not guaranteed dense maps to a contiguous copy taken inside the extension before any raw device pointer is formed, because the kernel reads rows at a dense stride; the caller keeps ownership, the callee borrows the pointer only for the launch and never frees it, and when the incoming tensor is already dense the copy is a no-op returning the same storage.
- General: a chain of separate elementwise and reduction library calls that share the projection result maps to one fused epilogue kernel per output row that re-reads that row in several sequential passes (a max-reduction pass, a sum-of-exponentials pass and a write pass), recomputing the activation in every pass instead of storing activated values, with each thread walking the row's columns through a lane-strided loop and the block combining per-lane partials through shared-memory tree reductions. This is valid only when a single thread block owns an entire output row; the fallback, required when blocks own only column tiles of the output, is to materialize the projection into device memory and launch the epilogue as a separate pass over that intermediate, which is why a tiled projection kernel writes a full-size intermediate that the epilogue launch then consumes.
- General: the exact (non-approximated) activation variant maps to the error-function form 0.5*v*(1+erf(v/sqrt(2))) evaluated in float32 on device; the hyperbolic-tangent approximation of the same activation is a fallback only, acceptable when its deviation stays inside the comparison tolerance, and substituting it silently is not equivalent.
- Source convention: when the source normalizes along dim 1 of a two-dimensional tensor, that axis is the feature axis and the contiguous inner axis, so map it to a row-wise max-shifted exponential normalized by a block-wide sum over the output columns; a lane-strided column loop plus a tree reduction over the block reproduces it, and normalizing any other axis is a different operator rather than a variant.
- General: where the target reports failures as thrown C++ exceptions that surface as host-language exceptions at the call boundary, validate rank, float32 dtype, reduction-length agreement between input and weight, and bias length before allocating or launching, so contract violations raise immediately instead of appearing as bad data at the next device synchronization.
- General: library-managed temporaries map to uninitialized device allocations made by the extension on the input's dtype and device options and returned to the caller as a new tensor that the caller owns and releases; the kernels must write every element because the allocation is not zeroed, and any full-size intermediate is freed when the entry function returns.
- Source convention: where the harness constructs both operators from the same seeded random state without loading any checkpoint, map the projection to the same parameter container and identical constructor arguments instead of raw tensors, because the drawn weights depend on parameter shapes and on creation order, and any deviation makes the two sides incomparable even when both are correct.
- General: an operator that must run entirely on the target device maps to an inline-compiled extension with a host prototype plus device kernel source, exposed through one entry point taking tensors and returning a tensor; because that extension is compiled when the module is imported, a missing host compiler or device-runtime header surfaces as a build/import error before any instance is constructed or any forward runs, and it must never be absorbed by degrading to source-side high-level ops, which the compute-path check rejects.
- Source convention: when the target API enqueues work on the caller's current device stream, map the operator to plain kernel launches on that stream, so the returned tensor is ordered with the caller's subsequent work without an explicit wait and any synchronization is added only for error attribution.
- Source convention: where the caller may relocate the module after construction (for example moving parameters to the device), map the projection by passing the parameter tensors into the extension on every call and re-deriving pointers there, instead of caching tensors, handles or raw pointers at construction time.

## Semantic deltas to expect

- Summation order changes: the library GEMM blocks the reduction over the feature length and may use tile-level or split reductions, while the custom kernel accumulates in fixed-step chunks in float32, so results agree only to a few units in the last place and equality must be tolerance-based.
- The activation is recomputed on every pass over a row instead of being stored, so the epilogue's transcendental work and its global-memory reads both scale with the number of passes (three in the visible control: max-shift maximum, exponential sum, normalized write); this is deterministic but changes runtime and traffic relative to the source chain.
- Peak device memory becomes explicit: one full-size intermediate plus one full-size output of batch by out_features in float32, both allocated by the extension, with the intermediate released on return, instead of an opaque library workspace.
- Failure timing differs: contract violations become synchronous exceptions from explicit checks, while launch and indexing faults surface asynchronously at the next device synchronization or as silently wrong values.
- Reduction scratch is per-block shared memory sized to the launch width; a block wider than the scratch, or a non-power-of-two width consumed by a halving tree, drops contributions instead of raising, so row sums fall below one.
- Numerics depend on the max-shift step: without it the exponential overflows above roughly 88 in float32 and rows collapse to non-finite values, whereas the source-side library call performs that shift internally.
- Row offsets must be 64-bit: batch times width can exceed a signed 32-bit range, and wrapped offsets read or write unrelated memory instead of failing.
- Cost is per row rather than per element: one block per row serializes a row's columns across the block, so epilogue time scales with batch times width divided by the block width and does not follow the projection's tile shape.
- The returned tensor is a fresh allocation rather than a library-owned buffer, so mutating the result is safe and the input and parameter buffers stay untouched.

## Pitfalls observed in successful migrations

- Reading the projection parameter as if it were stored (in_features, out_features): the kernel transposes implicitly or indexes out of range, giving wrong shapes or illegal reads; this occurs whenever the weight is stored output-first and the kernel was written for a reduction-first layout.
- Fusing the row-wide normalization into a tile-owned projection block: each block sees only a column slice of the row, so the denominator covers the tile and rows no longer sum to one; this occurs whenever the epilogue is attached to a launch whose grid tiles the output.
- Substituting the approximated activation for the exact one: a handful of elements exceed a 1e-4-style tolerance for mid-range activations, so a shape-correct result still fails comparison.
- Normalizing the wrong axis, or only a lane-strided subset of a row: the output looks plausible but each row does not sum to one; this occurs when the second axis of a two-dimensional input is mistaken for the batch axis, or when the write pass covers fewer columns than the reduction.
- Forming raw pointers from possibly non-dense or non-float32 caller tensors: rows are read at the assumed dense stride or reinterpreted at the wrong width, giving garbage; this occurs when the caller passes a view, a slice, or a differently typed tensor while only rank is validated.
- Omitting launch-status checking: a mis-sized grid or unsupported configuration appears as a delayed failure at the next synchronization and is misread as a numeric mismatch; this occurs whenever the port relies on the final comparison to reveal launch errors.
- Rebuilding parameters as raw tensors, or in an order different from the source container: the seeded initialization draws different values, so every element mismatches although both kernels are correct; this occurs when the new class drops the original parameter container or constructor arguments.
- Assuming the extension is built on first operator call: the inline build runs when the rebuilt module is imported, before the class can be constructed, so a missing host compiler or device-runtime header surfaces as an import/construction failure rather than as a wrong numeric result; this occurs whenever the build is expected to happen inside the forward path.
- Retuning the epilogue block width without resizing the shared reduction scratch or the halving loop: tail lanes are dropped and row sums drift; this occurs whenever launch configuration is changed independently of the reduction code.
- Caching parameter pointers or extension handles at construction: the caller may move the module to the device afterwards, so a captured pointer or weight tensor still refers to pre-move storage and the kernel reads stale or wrong-device memory; this occurs whenever the binding is done once at init instead of per call.

## Verification strategy

- Check shape, dtype and device of the returned tensor against the source contract, and that a forward returns a new tensor whose mutation leaves the input and parameter buffers unchanged.
- Check the model-free invariant: every row sums to one within float32 accumulation error and every entry is non-negative; this catches axis, max-shift and reduction-scratch errors with no reference run.
- Compare in stages on identical inputs (projection alone, then after the activation, then the full operator) using the caller's absolute and relative tolerance; the first stage that diverges localizes the defect.
- Drive pre-activations past the exponential overflow point by scaling the input or the weights, and confirm the output stays finite, which proves the max-shift pass runs.
- Exercise boundary shapes: one row, one output column, and a reduction length or row width that is not a multiple of the tile or block width, confirming padded lanes neither corrupt edges nor change row sums.
- Confirm repeatability: two calls on identical inputs return identical values, and several seeded input trials stay within tolerance, matching how the caller compares the reference and rebuilt operators.
- Synchronize explicitly after the call before comparing, so launch failures appear as errors at a known point instead of being conflated with numeric differences.
- Run several forwards and confirm the weight and bias are unchanged and that resident device memory does not grow steadily, which shows the intermediate allocation is actually released.

## Boundary

Covers only the forward rebuild of a two-dimensional float32 chain (affine projection, exact activation, feature-axis normalization) into device kernels, including the fusion boundary, buffer ownership, reduction strategy and the parameter-container convention needed for a seeded comparison. Two limits stay inside the covered area and matter to an implementer: the epilogue's block width must be a power of two no larger than the shared reduction scratch, so launch width and tree reduction are sized together and row width is never the bounded quantity; and the extension is compiled when its module is imported, so the build must succeed before any instance exists instead of failing during a forward. It does not cover backward or autograd, mixed or reduced-precision accumulation, batched or higher-rank inputs, distributing the projection across devices, replacing the kernels with vendor library calls, tile or occupancy tuning for peak throughput, or packaging the extension beyond the inline compile step.

Applicability constraints:

- The target runtime must expose a C/C++ device-extension entry point with an inline compile path, and a device math library providing a float32 error function, which the exact activation variant needs.
- Kernel source is compiled at import time, so a working host compiler and the platform device-runtime headers must be present in the evaluation environment; their absence surfaces as an import/build failure, not as a fallback to framework operators.
- The forward path must contain no framework tensor-library compute calls; only allocation, copy and layout helpers are available there, and the projection, activation and normalization arithmetic all have to live in the kernels.
- Designed for a single device, forward-only evaluation under no-grad with float32 inputs, parameters and outputs.
- Memory budget: one full-size intermediate plus one full-size output of batch by output width in float32 device memory, alongside the input and the weight; the intermediate is released when the entry function returns.
- Comparison is tolerance-based, around 1e-4 absolute and relative on float32; bit-exact equality with the source chain is not achievable.
- The epilogue assigns one thread block per output row and each thread walks that row's columns with a lane-strided loop, so the row width is independent of the block width: a row of many thousands of columns runs with a few hundred threads by looping over it. What is bounded is the block width, which must be a power of two no larger than the shared reduction scratch used by the tree reduction, and the design does re-read each row from global memory several times.
