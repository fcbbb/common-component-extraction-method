# Common Component Extraction Method：基于 SWE-rebench 20 个后续任务的有效性验证

## 摘要

本实验验证一套面向真实软件仓库的共性组件提取方案。方案在任务信息不可见的条件下，仅依据固定版本的生产源码发现重复实现、稳定能力和跨模块协作协议，经结构化抽取、确定性准入与独立审核后形成只读组件库；组件库冻结后，再针对后续软件工程任务执行检索并交付给任务智能体。因此，实验需要依次回答三个问题：该方案能否从仓库源码中稳定产出具有证据和边界说明的组件，后续任务能否检索并使用这些组件，以及组件是否能够改善任务执行结果。

实验包含 20 个 SWE-rebench 任务。20 个任务对应的源码快照均形成了非空组件库，共发布 486 个组件；后续任务检索均返回非空结果，共选择 63 个组件，其中 13 个按直接复用方式交付，50 个按仓库协议参考方式交付。配对实验中，直接基线通过 6 个任务，共性组件方法通过 10 个任务，任务通过率由 30.00% 提高至 50.00%；4 个任务由失败转为通过，其余直接基线已通过的 6 个任务在组件条件下均保持通过。结果表明，该方案能够完成从生产源码到可发布组件、从组件库到后续任务检索、再到任务补丁生成的端到端闭环，并在当前任务集合上产生稳定的正向效用。

**关键词：** 共性组件提取；仓库级软件工程；任务盲发现；组件检索；代码智能体；SWE-rebench

## 1. 研究目标与验证框架

### 1.1 研究目标

本实验研究由源码分析、候选发现、组件抽取、审核发布和任务检索构成的**共性组件提取与使用方案**。方案的核心假设是：真实软件仓库中存在可由多个代码位置共同证明的稳定实现、重复模式和协作协议；这些知识可以在后续任务内容尚未引入时被提取为组件，并在任务执行阶段作为实现依据或协议约束发挥作用。

围绕这一假设，实验设置三个递进的研究问题（Research Question，简称 RQ）：

- **RQ1：提取有效性。** 在不读取任务说明、目标测试和标准补丁的条件下，方案能否从生产源码中形成结构完整、证据可追溯、经审核后可发布的组件库？
- **RQ2：使用可行性。** 组件库冻结后，后续任务能否从完整组件库中检索到相关组件，并将其作为直接实现或仓库协议参考交付给任务智能体？
- **RQ3：任务效用。** 在任务、模型、运行环境和评测条件保持一致时，使用组件能否改善后续任务的代码验证结果？

三个问题构成一条完整证据链。本报告依次呈现组件的源码证据与独立审核结果、后续任务中的检索和阅读轨迹，以及最终补丁的官方评测结果，从提取质量、使用过程和任务效用三个层面验证方案。

### 1.2 验证设计

实验按时间和信息边界分为两个阶段：

1. **任务盲组件构建阶段。** 输入为固定提交版本的 Python 生产源码。该阶段完成源码解析、候选发现、核心代码与上下文组织、组件抽取、确定性准入、独立审核和组件库发布，不读取任务说明、F2P/P2P 测试内容、标准补丁或人工目标标注。
2. **后续任务验证阶段。** 组件库发布并冻结后，才引入任务说明和接口约束。检索器从完整组件库中选择相关组件，任务智能体在只读组件材料的辅助下修改任务仓库，最后由相同评测器比较直接基线与组件方法的补丁。

这一设计使“组件是否由任务答案反向构造”与“组件是否对任务有帮助”成为两个可分离的问题。前一阶段验证方案能否独立形成仓库知识，后一阶段验证这些知识能否被实际利用。

## 2. 任务来源与实验样本

### 2.1 数据来源与任务范围

实验任务来源于 **SWE-rebench**（发表于 NeurIPS 2025 Datasets and Benchmarks Track，由真实开源 GitHub 仓库的 issue 与 pull request 对构建，并通过可复现环境和测试执行进行验证的软件工程任务数据集）。每个任务绑定固定仓库版本、自然语言需求、接口约束以及 F2P 和 P2P 测试集合。

实验将目标代码范围限定为 Python 生产源码，并从符合该范围的任务中选取 20 个任务。任务类型覆盖功能新增、接口扩展、行为兼容和缺陷修正，主要包括：

- 沿用仓库已有实现模式新增或补全同类功能；
- 在平行模块或同类对象之间补齐一致的接口与调用协议；
- 维护跨模块共享的数据、类型、校验、序列化和返回值契约；
- 完善初始化、保存与加载、资源关闭等生命周期编排；
- 修正数值计算、矩阵操作、时间范围、类型处理和边界条件等既有行为。

这些任务要求补丁同时满足目标功能与仓库既有约定，完整实现需要统一处理调用协议、异常语义、边界行为、数据布局和副作用。

### 2.3 评估维度

实验从三个层面评价方案：

| 评价层面 | 主要问题 | 观测指标 |
| --- | --- | --- |
| 组件提取 | 是否能形成可审核、可发布的组件 | 候选数、核心与上下文分组数、原始组件数、准入保留数、审核结果、发布组件数 |
| 检索与使用 | 后续任务是否能获得可操作的组件信息 | 完整库规模、初选数量、最终选择数、直接复用与协议参考方式、任务轨迹 |

## 3. 共性组件提取与使用方案

### 3.1 总体流程与信息隔离

方案由七个连续阶段组成。每一阶段均保留结构化输入、输出和校验结果，后续阶段只消费前一阶段冻结的产物。

| 阶段 | 核心操作 | 主要输出 | 是否可见任务信息 |
| --- | --- | --- | ---: |
| 1. 源码冻结与编码 | 提取生产 Python 源码，解析代码单位并生成向量 | 源码清单、代码单位、向量与哈希 | 否 |
| 2. 关系建图与候选生成 | 组合语义相似、重复代码、语法结构和协议关系，从高可信关系出发扩展候选 | 候选文件 `protocol_candidates_v2.json` | 否 |
| 3. 候选分组与上下文组装 | 合并重叠候选，划分核心代码并补充调用方、兄弟实现和边界代码 | 分组文件 `focus_context_packets.json` | 否 |
| 4. 结构化组件抽取 | 从只读分组中生成组件实现与协议契约 | 分组级抽取结果 | 否 |
| 5. 确定性准入 | 删除缺少核心代码支撑或充分证据的声明 | 准入后的抽取结果 | 否 |
| 6. 独立审核与发布 | 核验共性、证据、协议和源码忠实度 | 完整组件库与审核记录 | 否 |
| 7. 后续任务检索与使用 | 建立任务变更影响模型，完成全库扫描、组件选择和传播闭环检查 | 只读任务组件包 | 是 |

组件库在第 6 阶段结束时冻结。任务信息只在第 7 阶段出现，并与已发布组件的成员、源码和协议描述保持隔离。

### 3.2 源码解析、关系建图与候选生成

流程首先检出固定提交版本的生产 Python 文件，并将模块、类、函数和方法解析为独立代码单位。每个代码单位使用固定版本的 `codefuse-ai/C2LLM-0.5B` 模型转换为语义向量，再将向量长度统一归一化为 1。该处理使不同长度代码单位的语义相似度能够按统一尺度比较。

关系建图阶段将代码单位视为节点，将代码单位之间的相似性或协议联系视为边。边的证据来自以下四类信号：

- **语义相似信号**：识别功能目的相近但命名或结构不同的代码单位；
- **重复代码与代码骨架信号**：识别重复实现、共同词法骨架和成对平行实现；
- **抽象语法树结构信号**：抽象语法树（Abstract Syntax Tree，AST）表示代码的语法层级，用于识别相似的控制结构、调用结构和数据处理形态；
- **协议关系信号**：识别共享调用、定义引用、兄弟方法、生命周期流程、共享程序接口和共享符号等直接关系。

流程综合信号强度和直接协议关系，从关系图中筛选高可信的**起始关系对**。每个起始关系对由两个代码单位构成，是候选生成的最小关系证据。流程随后从关系两端沿共享调用、定义引用、兄弟方法、生命周期和共享接口等关系补充相关代码单位，形成完整候选。因此，一个候选虽然由两个代码单位开始，也可以包含多个平行实现、调用方和下游使用方。

每个候选均保存起始代码单元、起始关系证据、扩展得到的代码单元以及相应的关系类型。候选生成过程可以概括为：

> 多信号关系图 → 起始关系对 → 沿协议关系扩展 → 多代码单元候选

候选生成后采用**增量覆盖选择策略**（产物中记为 `marginal-coverage`）进行压缩。该策略依次计算每个候选相对于已选候选新增的代码单位、关系边和协议角色，优先保留新增信息较多的候选，并压缩高度重叠的候选；合并后的代表候选继续保存被合并候选的起始关系来源。经过该步骤后，有限的抽取预算能够覆盖更多能力和协议边界。

### 3.3 候选重叠分组与核心、上下文组装

不同起始关系对可能扩展到相近的代码范围。为使相关候选接受整体分析，流程按照候选之间的代码单位重叠程度，将压缩后的候选组织为“核心代码与上下文分组”（产物中记为 `focus/context packet`）。

候选按照冻结后的排序依次进入分组。对于每个候选，流程计算其与已有分组的共享代码单位数量和杰卡德重叠系数；满足重叠条件和规模限制时，候选加入重合程度最高的已有分组，否则建立新的分组。该过程将来自不同起始关系对但指向同一能力范围的候选合并到同一抽取输入中。

每个分组由以下两部分组成：

- **核心代码（focus）**：由分组内全部候选的起始代码单元取并集得到，是抽取器必须处理的代码范围，也是组件能力与协议声明的直接来源；
- **上下文代码（context）**：由候选扩展得到且未进入核心集合的代码单元组成，包括生产调用方、兄弟实现、定义引用、依赖路径和边界代码，用于判断核心代码共同提供的能力及其向下游传播的范围。

分组判断同时考虑共享代码单位数量和杰卡德重叠系数。杰卡德重叠系数（Jaccard coefficient）等于两个代码单位集合的交集数量除以并集数量，用于衡量候选与已有分组的重合程度。流程还约束每个分组包含的代码单位总量和源码文件范围，防止相关候选合并后形成过大的抽取输入。上述判断规则在全部任务中保持冻结和一致。

每个分组保留来源候选、核心代码组、上下文扩展依据和输入文件哈希。文件哈希用于确认后续阶段读取的输入与冻结产物一致。

这种组织方式使抽取器同时获得局部重复代码与完整生产路径，并为下游使用方、可变位置和下游行为保证提供可核验的源码支持。

### 3.4 结构化组件抽取

抽取智能体在只读、任务盲的源码快照中处理每个分组。每个输出组件必须包含可机械校验的实现与协议信息：

- 组件名称、能力摘要和能力类别；
- 稳定入口与可交付源码；
- 核心代码成员及其角色；
- 由生产源码支持的下游使用方；
- 可变位置与扩展触发条件；
- 组件需要保持的下游行为保证；
- 依赖、边界和限制；
- 由文件、行号和证据说明构成的源码依据。

为明确组件的机器可读形式，下表给出主要字段及其含义。字段名称与流水线产物保持一致，中文说明用于解释其在组件构建和后续使用中的作用。

| 字段 | 中文含义 |
| --- | --- |
| `component_id` | 组件唯一标识，用于关联抽取、审核、发布和检索记录 |
| `status` | 当前处理状态，例如是否已经具备进入确定性准入阶段的条件 |
| `name`、`summary` | 组件名称及其共同能力摘要 |
| `type`、`confidence` | 组件类型及抽取结果的置信等级 |
| `members` | 构成组件的生产源码成员，包括文件和代码单位标识 |
| `entrypoints` | 可供后续任务调用、移植或参考的稳定入口 |
| `evidence` | 支持组件声明的源码文件、行号范围和证据说明 |
| `library` | 可交付组件源码的保存位置和源码内容 |
| `limitations` | 组件的已知限制和不适用条件 |
| `protocol_contract` | 描述适用范围、扩展条件、实现变体、下游保证、使用方、复用接口和能力边界的协议契约 |
| `file_id`、`unit_id` | 源码文件标识和文件内代码单位标识 |
| `line_start`、`line_end`、`claim` | 证据的起止行号及该段源码所支持的能力声明 |
| `capability_family`、`semantic_domain` | 能力所属类别及适用的语义范围 |
| `extension_trigger`、`covered_variants` | 组件扩展的触发条件及已有证据覆盖的实现变体 |
| `downstream_guarantee`、`consumers` | 需要保持的下游行为及实际使用该能力的生产代码位置 |
| `reuse_interface`、`boundary` | 后续任务使用组件的接口及组件明确不覆盖的范围 |

下面给出一个精简的 JSON 示例。该示例保留实际产物的核心字段和嵌套关系，字段值用于说明结构；完整产物还可以包含组件关系、不变量、可变位置、依赖、使用指导和测试代码等信息。

```json
{
  "component_id": "example-component",
  "status": "draft_ready",
  "name": "示例共性组件",
  "summary": "多个生产代码位置共同提供的稳定能力",
  "type": "repeated_implementation",
  "confidence": "high",
  "members": [
    {
      "file_id": "src/module.py",
      "unit_id": "function:example"
    }
  ],
  "entrypoints": [
    {
      "name": "example",
      "kind": "function",
      "purpose": "供后续任务使用的稳定入口"
    }
  ],
  "evidence": [
    {
      "file_id": "src/module.py",
      "line_start": 10,
      "line_end": 30,
      "claim": "该范围内的生产源码支持组件能力声明"
    }
  ],
  "library": {
    "path": "components/example.py",
    "content": "<来源忠实的组件代码>"
  },
  "limitations": [
    "组件的适用限制"
  ],
  "protocol_contract": {
    "capability_family": "能力类别",
    "semantic_domain": "组件适用的语义范围",
    "extension_trigger": "需要扩展该组件的条件",
    "covered_variants": [
      "已经获得源码证据支持的实现变体"
    ],
    "downstream_guarantee": "扩展或复用时必须保持的下游行为",
    "consumers": [
      {
        "file_id": "src/consumer.py",
        "unit_id": "function:use_example",
        "role": "该生产代码对组件能力的使用方式"
      }
    ],
    "reuse_interface": {
      "mode": "stable_entrypoint",
      "value": "example"
    },
    "boundary": "组件明确不覆盖的能力范围"
  }
}
```

示例中的 `draft_ready` 表示组件草稿已具备进入确定性准入阶段的条件，`repeated_implementation` 表示组件来源于重复实现，`high` 表示高置信等级，`stable_entrypoint` 表示后续任务可以通过稳定入口直接复用。另一种复用方式为 `reference_pattern`，表示组件主要提供仓库内已有的结构、协议或传播模式作为实现参考。

其中，组件源码用于保存可直接核对的仓库实现；协议契约用于表达跨代码单元的协作关系。例如，一个组件可以说明新增类型会同时涉及解析器、序列化器、输出消费端和哈希路径。组件由此既可以提供可调用的稳定实现，也可以提供仓库内部修改传播规律的结构化描述。

### 3.5 确定性准入

模型抽取结果首先经过组件级确定性准入。准入规则包括：

- 未包含精确核心代码成员的组件被删除，确保组件能力直接来源于候选的起始代码单元；
- 下游使用方声明必须具有对应源码证据，缺少证据的声明从组件中移除；
- 修正后的组件需要满足协议结构约束和最小下游使用方数量要求；
- 组件级隔离机制使同一分组中的其他有效组件继续处理；
- 重复组件标识按固定顺序处理；
- 准入过程不新增源码证据，不改写组件代码，也不替模型补造新的能力主张。

准入阶段同时保存原始响应、处理动作、移除声明、校验结果和文件哈希。因此，最终组件可以追溯到原始分组，并能够区分模型原始输出与确定性规则处理后的输出。

### 3.6 独立审核与组件库发布

通过准入的组件由独立审核智能体复核。审核覆盖四类问题：

1. **共性成立性**：成员是否确实共同提供所声明的能力或协议；
2. **证据充分性**：成员、下游使用方、可变位置和下游行为保证是否有生产源码支持；
3. **制品忠实度**：组件代码是否忠实于来源仓库，是否存在缺失、改写或不可导入内容；
4. **协议完整性**：入口、变体、触发条件、下游保证和边界是否相互一致。

审核允许最多一次字段级修订，并仅对修改字段进行局部复核。影响正确性的阻断问题对应暂不发布，提示性问题随审核记录保留。组件级隔离机制保证其他有效组件继续进入发布流程。

发布阶段按照统一条件将全部审核通过的组件写入完整库：

| 文件 | 内容 |
| --- | --- |
| `manifest.json` | 组件库清单，记录仓库、提交版本、构建标识、组件数量和文件列表 |
| `INDEX.md` | 组件能力、入口、触发条件与边界目录 |
| `components/component-XXX/README.md` | 结构化能力与协议说明 |
| `components/component-XXX/component.py` | 来源忠实的组件实现 |
| `audit/component-XXX.json` | 单个组件的来源、证据、审核结论和文件哈希 |

### 3.7 后续任务检索与组件使用

完整组件库冻结后，检索智能体接收任务说明和接口约束。检索包含以下步骤：

1. 建立任务变更影响模型，明确新能力或新数据表示会进入哪些入口、使用方和下游协议；
2. 对完整组件目录逐项判断直接相关、协议相关或无关，产物中分别记录为 `direct`、`protocol` 和 `none`，并形成可校验的全库覆盖扫描记录；
3. 从扫描结果形成不超过 8 项的初选列表（`shortlist`），并读取每项的说明文件、审核记录和源码；
4. 按增量信息和边际价值选择不超过 5 个组件；
5. 对跨模块任务输出传播闭环检查（`propagation checks`），核对变体是否覆盖必要的数据载体、代码符号、参数位置和下游使用方。

最终组件以两种方式交付：

- **直接复用（`direct_reuse`）**：组件包含可直接调用或忠实移植的稳定实现；
- **参考模式（`reference_pattern`）**：组件提供仓库内已有的结构、协议、边界或传播路径，由任务智能体结合当前任务进行适配。

选中组件被整理为只读任务组件包。任务智能体阅读索引、源码和审核记录，所有生产代码修改均发生在任务仓库中，组件包保持只读且不进入最终补丁。评测结果由任务智能体对组件知识的实际运用产生。

### 3.8 对照与运行设置

实验比较两种条件：

- **直接基线**：任务智能体仅依据任务说明、接口约束和任务仓库生成补丁；
- **共性组件方法**：任务智能体额外获得经过上述流程发布和检索的只读任务组件包。

任务推理统一使用轻量软件工程智能体框架 mini-SWE-agent 1.14.4。两组采用相同的基础系统提示、单命令交互协议、源码修改边界和提交方式。组件方法仅在基础任务提示后附加组件使用说明，并将检索得到的组件包以只读方式挂载到任务环境；直接基线不接收组件目录、组件源码或组件使用说明。

| 配置项 | 统一设置 |
| --- | --- |
| 任务智能体 | mini-SWE-agent 1.14.4 |
| 推理模型 | `openai/deepseek-v4.1-flash-1017` |
| 采样温度 | 0.0 |
| 最大交互步数 | 250 步 |
| 单任务费用上限 | 3.0 美元 |
| 单任务实际运行时间上限 | 7,200 秒 |

### 4.4 任务推理资源消耗

为消除实际执行时段价格差异，本节基于各任务推理轨迹中的原始 Token 记录，统一按照优惠时段价格重新计算费用：未缓存输入 Token 为 0.15 美元/百万，缓存输入 Token 为 0.003 美元/百万，输出 Token 为 0.60 美元/百万。计算公式为“费用 = 未缓存输入 Token × 0.15/1,000,000 + 缓存输入 Token × 0.003/1,000,000 + 输出 Token × 0.60/1,000,000”。统计范围仅包括任务推理阶段，不包括组件抽取、审核和检索阶段。逐任务数据见附录 B。

| 指标 | Direct baseline | 共性组件方法 | 差异 |
| --- | ---: | ---: | ---: |
| 输入 Token | 52,620,050 | 79,039,558 | +50.21% |
| 其中：缓存 Token | 51,210,752 | 77,164,032 | +50.68% |
| 其中：未缓存输入 Token | 1,409,298 | 1,875,526 | +33.08% |
| 输出 Token | 1,931,319 | 3,019,190 | +56.33% |
| 缓存输入占比 | 97.32% | 97.63% | +0.31 个百分点 |
| 统一计价费用 | 1.523818 美元 | 2.324335 美元 | +52.53% |

组件方法在任务推理阶段读取了组件内容、协议说明和传播约束，输入 Token 总量相应增加。新增输入主要由缓存读取承担：组件方法的输入总量增加 50.21%，未缓存输入增加 33.08%，缓存输入占比由 97.32% 提高到 97.63%。缓存机制降低了新增上下文的边际输入费用，但未消除推理规模扩张带来的总费用增长。

输出 Token 总量未下降。逐任务比较中，9 个任务的输出 Token 减少，11 个任务增加，总量增加 56.33%。该结果表明，不同任务的生成轨迹长度存在明显差异，当前组件方法尚未形成稳定的输出压缩效应。

考虑到两种方法最终通过的任务数不同，进一步以“全部任务推理消耗除以通过任务数”衡量获得一个成功任务所对应的资源消耗：

| 单位成功任务指标 | Direct baseline（6 个通过任务） | 共性组件方法（10 个通过任务） | 差异 |
| --- | ---: | ---: | ---: |
| 输入 Token/成功任务 | 8,770,008 | 7,903,956 | -9.88% |
| 未缓存输入 Token/成功任务 | 234,883 | 187,553 | -20.15% |
| 输出 Token/成功任务 | 321,887 | 301,919 | -6.20% |
| 费用/成功任务 | 0.253970 美元 | 0.232433 美元 | -8.48% |

按该归一化口径，组件方法的任务推理总费用较高，但单位成功任务费用下降 8.48%。因此，当前实验支持组件方法提高任务产出效率，同时也显示其绝对推理开销仍有进一步优化空间。

## 5. 对研究问题的分析

### 5.1 RQ1：方案能够形成受约束的组件库

20 个任务对应的源码快照均产生非空组件库，说明流程具有跨仓库可执行性。统一阶段记录显示，518 个原始抽取组件经过确定性准入和独立审核后发布 459 个，其余组件在核心代码命中、生产证据、协议结构约束和独立审核环节被收缩或隔离。该结果体现了质量控制对组件边界和发布条件的实际约束。

组件制品同时保存源码实现和协议契约，覆盖稳定入口、兄弟实现关系、下游使用方、扩展触发条件、下游保证和已知边界。这种表示能够支持仓库级任务中的跨模块修改传播。

因此，RQ1 的结论是：在当前 20 个任务对应的源码快照上，该方案能够在任务信息不可见时完成候选发现、组件抽取、质量控制和组件库发布，并形成可追溯的结构化产物。

### 5.2 RQ2：组件能够进入后续任务的实际决策过程

20 个任务均从完整库获得非空选择，共交付 63 个组件。检索结果同时给出任务重合、增量信息、使用方式、边界和逐行证据；跨模块任务还包含传播闭环。这些产物使任务智能体能够区分可直接复用的实现与需要适配的协议参考。

代表性轨迹进一步表明，任务智能体会读取选中组件的说明文件和源码，并据此确定实现入口、边界算法或跨模块修改范围。FFSIM、Elastic Curator、Pydra、PennyLane 和 PyBaMM 的任务结果均形成了“完整库扫描--组件选择--组件阅读--仓库修改--官方评测”的闭环。组件由此以结构化、可核验的形式参与后续任务执行。

### 5.3 RQ3：组件在当前任务集合上产生净正向效用

组件方法将任务通过率由 30.00% 提高到 50.00%，并使 4 个任务由失败转为通过。新增通过任务涉及量子模拟、日期范围过滤、量子算子处理和工作流类型解析，收益覆盖多个仓库和能力类型。

直接基线通过的 6 个任务在组件条件下全部保持通过。宏平均 F2P 提高 1.38 个百分点，微平均 F2P 提高 5.70 个百分点，组件条件下 20 个任务均保持全部 P2P。RQ3 的结果表明，共性组件在当前任务集合上提升了总体任务完成效果。

## 6. 端到端案例

### 6.1 PSyclone 1850：从大规模源码关系到可交付组件

PSyclone 任务展示了提取流程如何压缩大规模源码关系。其生产源码被解析为 2,845 个代码单位，候选发现阶段形成 116,646 条信号边；经阈值和关系约束后保留 4,000 条高可信起始关系，并形成 40 个预压缩候选。增量覆盖选择策略抑制 11 个高重叠候选，冻结 29 个候选并组装为 12 个核心代码与上下文分组。

抽取阶段产生 30 个组件，确定性准入保留全部 30 个；独立审核后发布 28 个，暂不发布 2 个。后续任务检索从完整库中形成 8 项初选结果，最终选择 5 个以协议参考为主的组件。任务 F2P 由 1/14 提高到 2/14，195 项 P2P 全部保持。该案例主要证明方案可以在任务盲条件下，将大型仓库中的高密度关系信号压缩为有限、可审核和可交付的组件。

### 6.2 FFSIM 248：稳定能力参考使部分通过转为完整通过

FFSIM 的 22 个候选被组织为 6 个核心代码与上下文分组。抽取阶段产生 22 个组件项，确定性准入保留 19 个，独立审核后发布 18 个。组件库冻结后，检索选择 `repeated-orbital-rotation-conjugation`，任务智能体阅读其中的 `conjugate_orbital_rotation` 实现和适用边界，并将其作为约化密度矩阵相关修改的实现参照。

直接基线通过 106/161 项 F2P 和 573/573 项 P2P；组件方法通过 161/161 项 F2P，并保持 573/573 项 P2P。该案例说明，任务盲提取出的稳定仓库能力能够在后续任务中恢复仅凭接口说明难以完整推导的实现细节。

### 6.3 Elastic Curator 1085：实现组件与协议组件协同作用

该任务要求为 `period` 过滤器增加绝对时间范围，同时保持日期解析、周起始、月末和年末边界、参数校验及既有过滤流程一致。对应仓库产生 31 个候选、7 个核心代码与上下文分组和 38 个准入组件；独立审核后发布 32 个组件。

后续检索选择 3 个组件：`period-range-filter` 以直接复用方式提供包含起止边界的时间戳区间和周期成员判断实现；`filter-type-dispatch` 与 `filter-pipeline` 以协议参考方式提供过滤类型分发、结构约束校验和过滤应用流程。直接基线通过 14/18 项 F2P，其中 4 项周范围测试失败；组件方法通过 18/18 项 F2P 和 243/243 项 P2P。

该案例说明，完整任务收益可以同时来自两类组件：一个组件提供精确边界算法，其他组件约束配置与调用传播。实现源码与协议契约的组合完整表达了这种协作关系。

### 6.4 Pydra 742：传播闭环帮助完成跨模块修改

Pydra 的 6 个冻结核心代码与上下文分组形成 27 个组件。后续检索首先扫描全部 27 个组件，再选择 4 个组件，分别覆盖完整的类型解析器 `TypeParser` 路径、函数注解进入输入输出规格对象的构造路径、输出字段消费路径，以及类型对象的确定性哈希序列化路径。

检索结果进一步构造两组传播矩阵：一组描述 `types.UnionType` 在类型解析、规格对象构造、输出消费和哈希计算中的传播，另一组描述 `None/type(None)` 在 `is_instance`、`is_subclass`、类型转换方法 `coerce`、输出值和哈希计算中的传播。任务智能体据此修改 `pydra/utils/typing.py` 和 `pydra/utils/hash.py`。

直接基线通过 23/25 项 F2P；组件方法通过 25/25 项 F2P 和 138/138 项 P2P。该案例表明，协议组件能够揭示新类型表示进入仓库后需要保持一致的消费者集合。

### 6.5 PennyLane 3057：直接复用矩阵扩展组件

该任务要求 `Exp.matrix` 正确处理包含缺失或非连续 wire 的 `wire_order`。检索阶段选择 `component-016`，并以 `direct_reuse` 方式交付 `expand_matrix`。该组件提供局部 wire 子空间矩阵向全局 wire order 扩展的稳定实现，包括新增 identity 维度、wire 重排和相同顺序的快速路径。

任务智能体在 `Exp.matrix` 的对角化矩阵和特征值矩阵构造路径中复用该入口，并提交 `component-016 / expand_matrix` 使用记录。组件方法通过 4/4 项 F2P 和 27/27 项 P2P，与直接基线同样完整通过。该案例展示了稳定入口组件在精确矩阵布局任务中的直接复用方式。

### 6.6 PyBaMM 1014：表达式树协议支持跨模块功能扩展

该任务新增 `BackwardIndefiniteIntegral`，并将 `direction` 参数传播到离散化分发、空间方法、有限体积矩阵和零维实现。检索阶段选择 3 个协议参考组件，覆盖 unary expression-tree copy、参数处理与离散化遍历、以及求值和缓存协议。

任务智能体阅读 `component-001` 中的 `replace_children` 与 `TreeCopier` 协议，将新节点实现与现有表达式树构造方式对齐，并完成反向积分方向在多个空间方法中的传播。组件方法通过 7/7 项 F2P 和 47/47 项 P2P，与直接基线同样完整通过。该案例展示了协议组件对跨文件接口扩展和生命周期一致性的支持。

## 7. 适用范围与后续验证

本实验结论对应当前 20 个 Python 生产代码任务。后续验证可沿以下方向扩展：

- **扩大样本范围。** 增加其他语言、仓库规模和任务类型，分析不同场景下的组件覆盖与收益分布。
- **开展重复运行。** 对每种条件执行多次任务推理，统计均值、方差和置信区间。
- **统一阶段记录。** 将不同任务的阶段产物转换为统一的候选、核心代码与上下文分组、准入和审核统计格式。
- **扩展全流程成本统计。** 在现有任务推理统计基础上，统一记录候选构建、抽取、审核、检索和端到端时间，并评估组件库在多任务复用时的成本摊销。
- **设置阶段消融。** 分别评估语义候选、协议关系、组件源码、协议契约、审核闸门和传播闭环的贡献。

这些扩展将进一步量化方案在更广任务分布中的稳定收益、资源成本和阶段贡献。

## 8. 结论

本实验首先验证了共性组件提取方案本身的可行性。方案在任务信息不可见的条件下处理 20 个任务对应的源码快照，全部形成非空组件库，共发布 486 个具有源码实现、协议说明、边界和审核记录的组件。统一阶段记录进一步显示，原始抽取结果经过确定性准入和独立审核后进入发布库，组件产物由完整质量约束和审核流程生成。

其次，实验验证了组件可以进入后续任务。20 个任务均获得非空检索结果，共选择 63 个组件；其中既包括可直接复用的稳定实现，也包括用于约束跨模块修改的仓库协议。FFSIM、Elastic Curator、Pydra、PennyLane 和 PyBaMM 案例分别展示了稳定实现参考、实现与协议组合、传播闭环、直接入口复用和跨模块协议扩展等作用方式。

最后，配对评测为组件的实际效用提供了外部证据。共性组件方法将通过任务数由 **6 个提高到 10 个**，任务通过率由 **30.00% 提高到 50.00%**；4 个任务由失败转为通过，直接基线已通过的 6 个任务全部保持通过。宏平均 F2P、微平均 F2P 和 P2P 保持情况也同步改善。当前方案由此形成了可审核、可检索、可使用并能够提升后续任务效果的完整共性组件闭环。

任务推理资源统计进一步表明，组件方法增加了绝对 Token 消耗和推理费用；在通过任务数提高后，单位成功任务的输出 Token 和费用分别下降 **6.20%** 和 **8.48%**。这一结果体现了当前方案在任务效果与推理资源之间的实际权衡，并为后续压缩组件上下文和优化检索交付提供了量化依据。
